# F12.5 Batch — MVP capability/scope gate

Date: 2026-10-14

## Decision

F12.5 starts with **Text Watermark only** as the first batch operation.

This is a scope gate, not a promise that every existing utility becomes batch-capable.

## Why Text Watermark first

Existing code already has the complete local/offline path:

`WatermarkUtilityRequest → WatermarkPlanner → PdfTextOverlayWriter.SaveAsCopy(...)`

The current single-document UI proves that the writer:
- receives an explicit source path and destination path;
- captures/uses source fingerprint protection;
- writes a copy rather than replacing the source;
- reports success/failure;
- needs no new PDF engine, network service or package.

This makes Text Watermark the smallest operation that can prove the Batch architecture by **reusing an existing owner instead of duplicating a pipeline**.

## Candidate audit

| Candidate | Existing owner | Decision for first MVP | Reason |
|---|---|---|---|
| Text Watermark | `WatermarkPlanner` + `PdfTextOverlayWriter` | **GO / FIRST** | smallest proven local Save-As path |
| Bates / page numbering | `PageNumberingPlanner` + same `PdfTextOverlayWriter` | DEFER | good second candidate after Batch reuse is proven |
| Password protection | `PdfProtectionWriter` + qpdf | DEFER | async + password/security semantics increase first-slice complexity |
| OCR | existing OCR workflow/Tesseract | DEFER | heavier operation, progress/cancel and corpus concerns |
| Organize | organize plan/materialization workflow | DEFER | structural/session semantics; not needed to prove Batch |
| Conversions | F12.7 | OUT OF F12.5 | separate capability/quality gates by roadmap |

## KISS architecture decision

Do **not** create:
- generic `BatchEngine`;
- workflow designer;
- job database;
- queue/worker/scheduler;
- pipeline framework;
- operation plugin system;
- second PDF engine;
- cloud/backend dependency.

The Batch slice should be a thin sequential coordinator around existing operation owners.

## D2.1 minimal contract

Create only the product vocabulary needed before execution exists:

- explicit input PDF paths;
- explicit output directory;
- exact operation enum, initially only `TextWatermark`;
- per-item result with input path, output path, success and optional error.

No execution service and no UI in D2.1.

## Next after D2.1

D2.2 will prove reuse with **one Text Watermark item** before any multi-file loop or UI is introduced.

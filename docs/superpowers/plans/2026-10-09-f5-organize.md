# F5 Organizar PDF Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement `ORGANIZAR` as a safe, offline, plan-first PDF page workspace for reorder/rotate/delete/duplicate/insert/merge/extract/split, with conservative structural preflight and transactional `Guardar como...` output.

**Architecture:** Keep PDFium as the only PDF engine. UI actions mutate an in-memory `OrganizePlan`; native PDF materialization happens only when producing an output. `ORGANIZAR` has a dedicated virtualized thumbnail surface separate from F4 `LEER`, F3 `FIRMAR` and ZPL. Outputs are composed into a new temporary PDF with exact page imports, planned rotation, close/reopen validation and atomic publication. Cryptographically signed PDFs and password-required PDFs are blocked from F5 structural output/import in the initial version.

**Tech Stack:** C# / .NET 10 / WPF / PDFium `bblanchon.PDFium.Win32` 156.0.8076 / existing PDFsharp 6.2.4 for deterministic synthetic fixtures / xUnit. No new runtime package.

**Spec:** `docs/superpowers/specs/2026-10-09-f5-organize-design.md`

**Exact base:** F4 closure `1d620f1b2b9717aab35671e18a9dc78f28a8afdd`.

## Global Constraints

- Windows x64 + C#/.NET 10 + WPF.
- PDFium remains the only PDF engine in F5 unless a later demonstrated gap is separately approved.
- All PDFium calls use the same `PdfiumRuntime.NativeGate` semaphore (`Wait`/`Release`); no `lock(NativeGate)` path may remain.
- No cloud, HTTP service, account, API key, telemetry, database, WebView2 or runtime network dependency.
- No new runtime NuGet package for F5.
- `Guardar como...` only: never overwrite the active source PDF in initial F5.
- Never publish output before temp save + close + reopen + validation succeeds.
- Runtime validation renders every output page sequentially at 36 DPI, one bitmap at a time.
- Cryptographic signature count > 0 = Block.
- A source that required a password to open = Block for structural output/import.
- `UNKNOWN` preservation is never presented as preserved.
- Plan/state logic remains independent from WPF; writer remains independent from tile controls.
- Do not expose raw PDFium handles broadly.
- F4 LEER, F3 FIRMAR and F2 ZPL remain regression gates.
- Earlier manual/private/physical QA stays NOT RUN unless actually executed.
- No merge to `main` without explicit user approval.
- Execute one task at a time. At F5.1/F5.2/F5.3/F5.4/F5.5 checkpoints, push and require exact-head Windows CI PASS before proceeding.

## Review Focus

1. **Non-contiguous multi-selection moved forward/backward** preserves relative order with no duplicate/lost IDs. Test: `MoveSelection_NonContiguousForwardBackward_PreservesRelativeOrderWithoutLoss` (Task 2).
2. **Secondary source disappears/changes after being added** fails before publication and preserves the destination. Test: `SaveAsCopy_SourceChangedOrMissingBeforeMaterialization_PreservesDestination` (Task 4/7).
3. **Very large organize workspace** never eagerly renders all thumbnails. Test: `LargeDocument_OnlyRealizedPlusNeighborThumbnailsHoldBitmaps` (Task 5).
4. **Split output collision** blocks before first bulk write; no silent overwrite. Test: `SplitPublish_AnyExistingTarget_BlocksBeforeFirstWrite` (Task 8).
5. **Noncrypto structures not proven preserved** require explicit warning; signed/password sources always block. Test: `Preflight_UnknownOrChangedNonCryptoStructure_RequiresExplicitWarning` (Task 9).

## Task 0 — Prerequisite: Repair F4 NativeGate Concurrency Mismatch

**Why this exists:** audit of the F5 base found `PdfDocumentSession.Navigation.cs` using `lock (PdfiumRuntime.NativeGate)` while `PdfiumRuntime.NativeGate` is a `SemaphoreSlim` and every render/text/session path uses `Wait()/Release()`. `lock` and semaphore acquisition do not synchronize, so bookmark/link calls can overlap another PDFium call. F5 must not build more native editing on this inconsistent gate.

4. assert the call does not complete while the semaphore is held;
5. release the semaphore;
6. assert the call completes.

Expected RED on current F4 base: navigation can complete while the semaphore is held because it only takes the object's monitor lock.

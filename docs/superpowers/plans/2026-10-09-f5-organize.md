# F5 Organizar PDF Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement `ORGANIZAR` as a safe, offline, plan-first PDF page workspace for reorder/rotate/delete/duplicate/insert/merge/extract/split, with conservative structural preflight and transactional `Guardar como...` output.

**Architecture:** Keep PDFium as the only PDF engine. UI operations mutate an in-memory `OrganizePlan`; native PDF materialization happens only when an output is requested. A dedicated organize surface is separate from F4 `LEER`, F3 `FIRMAR` and ZPL. Outputs are composed into a new temporary PDF with exact page imports, planned rotation, save/reopen validation and atomic publication. Cryptographically signed PDFs and password-required PDFs are blocked from F5 structural output/import in the initial version.

**Tech Stack:** C# / .NET 10 / WPF / PDFium `bblanchon.PDFium.Win32` 156.0.8076 / existing PDFsharp 6.2.4 test-fixture capability / xUnit. No new runtime package.

**Spec:** `docs/superpowers/specs/2026-10-09-f5-organize-design.md`

**Exact base:** F4 closure `1d620f1b2b9717aab35671e18a9dc78f28a8afdd`.

## Global Constraints

- Windows x64 + C#/.NET 10 + WPF.
- PDFium remains the only PDF engine in F5 unless an explicit later gap decision is approved.
- Every new PDFium call stays behind `PdfiumRuntime.NativeGate`.
- No cloud, HTTP service, account, API key, telemetry, database, WebView2 or runtime network dependency.
- No new runtime NuGet package for F5.
- `Guardar como...` only: never overwrite the active source PDF in initial F5.
- Never publish an output before temp save + close + reopen + validation succeeds.
- Runtime validation renders every output page sequentially at 36 DPI; do not replace this with sampling without evidence and a design change.
- Cryptographic signature count > 0 = block F5 structural output.
- A source that required a password to open = block F5 structural output/import.
- `UNKNOWN` preservation status is never presented as preserved.
- Plan/state code must remain independent from WPF.
- Native writer must remain independent from UI tile controls.
- Do not expose raw PDFium document handles broadly.
- F4 LEER, F3 FIRMAR and F2 ZPL remain regression gates.
- Manual/private/physical gates from earlier phases remain NOT RUN unless actually executed.
- No merge to `main` without explicit user approval.
- Execute one task/checkpoint at a time; push and wait for exact-head Windows CI before proceeding across slice boundaries.

## Review Focus

These are the five highest-risk behaviors. Each has an owning automated test below.

1. **Non-contiguous multi-selection moved forward/backward** must preserve exact relative order with no duplicate/lost page IDs. Owning task: Task 2, `MoveSelection_NonContiguousForwardBackward_PreservesRelativeOrderWithoutLoss`.
2. **A secondary source disappears or changes after being added** must fail before publication and preserve both current plan and existing destination. Owning task: Task 4/7, `SaveAsCopy_SourceChangedOrMissingBeforeMaterialization_PreservesDestination`.
3. **Very large organize workspace** must not eagerly create/render all thumbnails. Owning task: Task 5, `LargeDocument_OnlyRealizedPlusNeighborThumbnailsHoldBitmaps`.
4. **Split output collision** must be detected before the first bulk write; existing files must never be silently overwritten. Owning task: Task 8, `SplitPublish_AnyExistingTarget_BlocksBeforeFirstWrite`.
5. **Document-level structures that are not proven preserved** must surface an explicit warning, while signed/password-required sources always block. Owning task: Task 9, `Preflight_UnknownOrChangedNonCryptoStructure_RequiresExplicitWarning`.

KISS algorithm:

2. capture source file identity needed to detect obvious stale/missing sources before write (at minimum normalized path, length and last-write UTC captured when source enters the plan; add these fields to `OrganizeSource` if this test proves necessary);

8. close all native handles;
9. reopen/validate output;
10. atomically replace/move destination;
11. temp cleanup in `finally`.

## Stop Conditions

Stop implementation and return to design review if any of these occurs:

1. pinned PDFium lacks a critical writer API and no simple equivalent PDFium route exists;
2. correct page import requires a second engine to satisfy core ORG-01/02 rather than an edge preservation case;
3. writer output cannot be made transactional without source overwrite risk;
4. F5 requires storing/reusing PDF passwords;
5. preserving a required structure demands a generic low-level PDF object graph rewrite;
6. WPF thumbnail virtualization would require a large custom framework instead of a simpler usable layout;
7. F3/F4/F2 regressions cannot be isolated with a narrow change.

A stop condition is evidence, not permission to expand scope automatically.

# History — 2026-10-08 — F3.2 Photo/Scan Signature Preparation

## Outcome

F3.2 reached **automated PASS** on `feat/f3-2-photo-preparation` / PR #20 draft. SG PDF Editor can now create a transparent visual-signature asset from a local PNG/JPG/JPEG photo or scan of a dark/blue signature on white or near-white paper, then feed that asset into the existing F3.1 placement/save flow.

## Product behavior added

- local PNG/JPEG photo loader;
- shared decoded-image safety limit of 20,000,000 pixels;
- immutable BGRA `SignaturePhotoSource`;
- deterministic paper-color estimation from light perimeter samples;
- soft alpha background removal instead of binary thresholding;
- original alpha multiplication/preservation;
- bounded background-removal, brightness and contrast controls;
- ink styles Original / Negro / Azul (`#194196`);
- usable-content rejection for blank/noise-only results;
- automatic crop with bounded padding;
- focused WPF `Preparar firma` dialog with checkerboard transparency preview;
- preview capped at 1200 px longest side;
- stale async preview results blocked by a version gate;
- UI-thread preview application through WPF Dispatcher;
- final Apply always reprocesses the full source;
- `Crear desde foto...` button integrated into FIRMAR;
- cancel/failure preserves existing placements, selection and dirty state.

## Architecture

F3.2 is preprocessing only. It does not introduce a second signature model or touch the PDF writer. All paths converge to the existing F3.1 `SignatureAsset` and `AddSignatureAsset(...)` placement flow.

The photo remains local. No temporary signature image is required in the normal path. No runtime network, cloud background remover, AI/ML, OCR or new image-processing package was introduced.

### Ruling — one paper color for preview and final

The approved plan contained an older sentence allowing the reduced preview to estimate paper separately. During self-audit this was superseded: `SignaturePhotoDialog` estimates `SignaturePaperColor` once from the immutable full-resolution source and reuses that exact value for both reduced preview and final Apply. This prevents preview/final drift caused solely by downsampling.

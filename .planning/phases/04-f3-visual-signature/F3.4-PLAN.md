## Product contract

F3.4 persists and reloads the existing `SignatureAsset` locally. It does not persist PDF placement geometry and does not create a second signature/PDF pipeline.

```text
existing SignatureAsset
  ↓ save
%LOCALAPPDATA%\SG PDF Editor\Signatures\
  library.json + <guid>.png
  ↓ load
existing SignatureAsset
  ↓ Use
existing AddSignatureAsset(...)
```

## Frozen behavior

- local/offline only; no cloud/account/database/encryption claim;
- manifest v1 is authoritative and corruption is preserved, not auto-repaired;
- GUID-based physical PNG names; display names are metadata only;
- duplicate display names rejected case-insensitively after trim;
- lossless transparent PNG, existing 20M-pixel loader guard;
- safe same-directory temp/publication ordering for Add/Rename/Delete;
- broken PNG affects only its item; orphan PNG is ignored;
- Save selected stores the exact selected placement's `SignatureAsset` without changing PDF state;
- successful Use returns an asset and invokes existing `AddSignatureAsset(...)` exactly once;
- no new package, PDF writer/coordinate change, ZPL change or MainWindow framework refactor.

## Review focus

1. corrupt manifest never silently overwritten;
2. Add cannot publish a manifest reference before its PNG exists;
3. Delete cleanup failure leaves a logical delete + harmless orphan;
4. one broken PNG never poisons healthy entries;
5. cancel/failure preserves PDF state; successful Use delegates once to F3.1 placement flow.

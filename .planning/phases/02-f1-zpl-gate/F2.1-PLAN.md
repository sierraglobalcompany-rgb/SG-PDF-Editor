# F2.1 — ZPL Parse + Open

**Date:** 2026-10-07  
**Branch:** `feat/f2-1-zpl-parse-open`  
**PR:** #13 draft, base `design/f2-labelize-architecture`, no merge  
**Status:** functional implementation automated PASS; final docs/head verification pending

## Goal

Add the first production ZPL slice without yet invoking Labelize: open local `.zpl/.txt/.prn`, parse printable designs, preserve `^PQ` as quantity metadata, retain document-level stored-format context, and safely switch the WPF workspace only after a valid parse.

## Scope

- immutable `ZplDocument` / `ZplDesign` model;
- pure managed `ZplDocumentParser`;
- complete `^XA...^XZ` block validation;
- `^DF` support blocks excluded from user-visible designs while source order is preserved;
- `^PQ` extracted as metadata and removed from `NormalizedRenderSource`;
- strict local UTF-8 loader for `.zpl/.txt/.prn`;
- WPF `Archivo > Abrir etiquetas ZPL...`;
- safe PDF ↔ ZPL workspace replacement;
- no Labelize process/runtime package yet.

## Out of scope

- Labelize sidecar invocation;
- PNG preview;
- quantity-selection UX;
- thermal dimensions/layout/PDF export/printing;
- private Mercado Libre fixtures in Git;
- physical printer/scanner validation.

## Accepted semantics

- absent `^PQ` => quantity 1;
- `^PQ0` => quantity 1;
- multiple `^PQ` in one printable block => last quantity wins;
- every `^PQ` is removed from render input;
- quantity maximum: 99,999,999;
- malformed/out-of-range `^PQ` => controlled `InvalidDataException`;
- `^PQ` inside a `^DF` stored-format definition is rejected in F2.1 rather than silently guessed;
- `TotalQuantityFromFile` is `long`;
- invalid ZPL never replaces the current valid workspace.

## Implementation notes

- Label UI integration lives in `MainWindow.Labels.cs`, a partial of the existing window, to avoid further inflating the already-large `MainWindow.xaml.cs`; this adds no ViewModel/service/framework.
- `OpenZplMenuItem.IsEnabled` follows `OpenPdfMenuItem.IsEnabled`, so existing busy-state behavior remains the single source of truth.
- successful ZPL commit disposes the prior PDF session only after parsing succeeds;
- successful PDF rendering clears any prior loaded-ZPL reference when the PDF image becomes visible;
- private/customer ZPL is not versioned and is not required for automated CI.
